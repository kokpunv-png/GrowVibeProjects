# PRD: Мониторинг новых торговых точек и точек услуг в Акмолинской области

|---|---|

| **Регион охвата** | Акмолинская область (РК) |
| **Связанный документ** | `TZ_monitoring_novyh_tochek_Akmola.md` — техническая детализация |

## 1. Проблема

Информация об открытии новых магазинов, кафе и точек услуг в Акмолинской области рассредоточена по десяткам источников (региональные СМИ, официальные страницы акимата, госреестры, соцсети, картографические сервисы) и нигде не собирается в единую регулярную сводку. Ручной сбор такой информации за месяц требует десятков поисковых запросов и всё равно даёт неполную и неструктурированную картину: крупные объекты (ТРЦ, заводы, соцобъекты) освещаются хорошо, а рядовые магазины, аптеки, салоны красоты и СТО — почти никогда.

Как следствие, у бизнес-аналитиков, инвесторов, маркетологов и представителей самого региона нет удобного и актуального инструмента, чтобы отслеживать динамику развития торговли и сферы услуг области помесячно.

## 2. Цель продукта

Дать пользователю **автоматический, регулярный и структурированный отчёт** о новых торговых точках и точках предоставления услуг, открывшихся в Акмолинской области за прошедший месяц, без необходимости вручную искать и сверять информацию по десяткам источников.

### 2.1. Задачи
1. Автоматически находить упоминания новых объектов торговли и услуг во всех доступных открытых источниках.
2. Структурировать найденную информацию в единый формат (название, категория, адрес, дата, источник).
3. Отсеивать дубли и низкодостоверные/рекламные упоминания.
4. Ежемесячно, к 1-му числу, предоставлять готовый отчёт за прошедший месяц.

## 3. Целевые пользователи

| Персона | Потребность |
|---|---|
| Аналитик регионального акимата / управления предпринимательства | Отслеживать деловую активность и динамику МСБ по районам |
| Инвестор / девелопер коммерческой недвижимости | Понимать, какие форматы и сети заходят в регион, где концентрация роста |
| Маркетолог федеральной сети (продукты, аптеки, услуги) | Мониторить конкурентов и незанятые ниши по районам |
| Журналист / исследователь региональной экономики | Быстро получать фактуру для материалов без ручного сбора |

## 4. Пользовательские сценарии (User Stories)

1. *Как аналитик акимата*, я хочу 1-го числа месяца получать таблицу всех новых точек за прошлый месяц с разбивкой по районам, чтобы включать это в отчёт о деловой активности.
2. *Как инвестор*, я хочу видеть, какие сети и в каких форматах заходят в конкретные районы области, чтобы оценивать инвестиционную привлекательность локаций.
3. *Как пользователь*, я хочу видеть источник и ссылку на каждую запись, чтобы самостоятельно проверить достоверность.
4. *Как пользователь*, я хочу фильтровать отчёт по категории (торговля/услуги/общепит) и по району.
5. *Как пользователь*, я хочу получать отчёт автоматически (email/Telegram), не заходя специально в систему.

## 5. Объём (Scope)

### 5.1. Входит в MVP
- Автоматический ежемесячный сбор данных из бесплатных открытых источников: региональные и республиканские СМИ, официальные страницы акимата, открытые госреестры.
- Структурирование в таблицу с полями: название, категория, населённый пункт/район, адрес (если найден), дата, источник, ссылка, уровень достоверности.
- Дедупликация упоминаний одного объекта из разных источников.
- Отчёт за месяц в табличном виде (CSV/Excel) + краткая сводная статистика.
- Доставка отчёта на email и/или в Telegram.

### 5.2. Вне MVP (следующие итерации)
- Интеграция с платным API 2ГИС для отслеживания новых карточек организаций.
- Мониторинг соцсетей (Instagram, TikTok, Facebook) по гео-тегам.
- Интеграция с реестром юрлиц/ИП по кодам ОКЭД и дате регистрации.
- Веб-дашборд с картой и историей по месяцам.
- Автоматическая геокодировка адресов и визуализация на карте.
- Расширение на другие области Казахстана.

### 5.3. Явно не входит
- Ручной обзвон/проверка каждой точки на месте.
- Гарантия 100%-й полноты (мелкий бизнес системно недопредставлен в открытых источниках — см. риски).

## 6. Функциональные требования (по приоритету)

| Приоритет | Требование |
|---|---|
| P0 | Автозапуск сбора данных 1-го числа месяца за предыдущий календарный месяц |
| P0 | Сбор из источников: СМИ, акимат, госреестры (см. ТЗ, п. 4.1–4.3) |
| P0 | Извлечение и структурирование ключевых полей (название, категория, район, дата, источник) |
| P0 | Дедупликация записей об одном и том же объекте |
| P0 | Формирование табличного отчёта за месяц |
| P0 | Доставка отчёта пользователю (email или Telegram) |
| P1 | Отдельный столбец точного адреса (улица, дом), где доступен |
| P1 | Оценка уровня достоверности записи (высокий/средний/низкий) |
| P1 | Фильтрация отчёта по категории и району |
| P2 | Веб-дашборд с историей отчётов и динамикой по месяцам |
| P2 | Интеграция 2ГИС API |
| P2 | Мониторинг соцсетей |

## 7. Нефункциональные требования

- Отказоустойчивость: недоступность одного источника не должна прерывать весь процесс сбора.
- Отчёт должен формироваться не позднее 09:00 (Астана) 1-го числа месяца.
- Логирование всех запусков и ошибок сбора.
- Соблюдение условий использования источников (robots.txt, лимиты API).
- Возможность ручной модерации записей перед отправкой отчёта (на начальном этапе — обязательна, т.к. NLP-извлечение может ошибаться).

## 8. Метрики успеха

| Метрика | Целевое значение (ориентир) |
|---|---|
| Доля успешных автозапусков без сбоев | ≥ 95% |
| Среднее число найденных объектов в месяц | Базовая метрика для отслеживания роста охвата от версии к версии |
| Доля записей с подтверждённым районом | 100% |
| Доля записей с точным адресом | Отслеживать как метрику качества, целевое значение определить после MVP (реалистично: 20–40% на старте) |
| Доля дублей в финальном отчёте | ≤ 5% |
| Время от запуска до готового отчёта | ≤ 2 часов |

## 9. Риски и допущения

1. **Неполнота открытых данных.** Мелкий бизнес системно недопредставлен в публичных источниках — метрика охвата на старте будет далека от 100% реальных открытий. Это ожидаемое ограничение MVP, а не дефект.
2. **Задержка публикаций.** Часть объектов будет упоминаться в СМИ с опозданием на недели/месяцы — требуется логика отнесения записи к месяцу по дате открытия, а не по дате публикации.
3. **Качество NLP-извлечения.** Автоматическое извлечение адреса/даты из неструктурированного текста может давать ошибки — на MVP-этапе закладывается этап ручной модерации.
4. **Зависимость от доступности источников.** Изменение структуры сайтов-источников или ограничение доступа (rate limits, платный API) может потребовать доработки парсеров.
5. **Допущение.** Пользователь согласен с тем, что MVP даёт репрезентативную, но не исчерпывающую картину, и полнота будет расти по мере подключения платных источников (2ГИС API, госреестр по ОКЭД).
